# pi-pleat 框架

为超长时间 agent 工作以及超长对话而生。

状态：设计基线，尚未实现插件。目标宿主为 Pi 1.2.0。实测结果见
[验证记录](validation.md)，开发前的验证门槛见[路线图](roadmap.md)。

模块职责、数据来源和提交规则按本文执行；服务商能力、恢复和完整响应处理仍须通过列出的验证，不能由设计说明代替测试。

`docs/pi_context_management_plan.md`为早期方案.

## 1. 产品范围

pi-pleat 管理当前会话的上下文大小和压缩过程。处理顺序是清理旧工具结果、按需取回结果，
最后在达到阈值时压缩历史。thinking 默认保留，由支持的原生压缩方法处理被摘要范围内的推理。

首版使用 Pi 的会话树、压缩条目和 `context_edit`。模型只获得一个 `recall` 工具；
用户通过 `/context` 查看状态。首版不加入跨会话记忆、数据库、语义索引、后台压缩或
额外的阈值配置。

插件与其他修改历史或接管压缩的扩展互斥。只在首次发送前改写工具结果的扩展可以共存。
Pi 1.2.0 把 `tool_result` 和 `message_end` 改写后的结果写入 JSONL，模型看到的也是这个版本
（见[验证记录](validation.md#仓库复测)），所以召回不会绕过在这两处脱敏的扩展。只在每次请求时
临时改写内容的扩展（例如使用 `context` 事件）不改变 JSONL；它能否遮住召回的输出，取决于它
是否处理所有工具的结果。

## 2. 设计原则与约束

### 设计原则

1. Anthropic 优先适配 preserved thinking。会话内 `system` 和 `tools` 保持不变，客户端不修改已经发送的消息。旧工具结果只由服务端清理；取回内容作为新的工具结果追加。
2. 上下文管理优先使用官方原生方法：Anthropic 服务端清理和按需压缩、OpenAI 独立压缩、Codex 官方客户端的 Responses-trigger，以及 Pi 的 `context_edit` 和压缩条目。插件代码只处理这些方法没有覆盖的部分：召回、非 Anthropic 通道的清理选择，以及 Pi 尚未支持的原生压缩响应和回放。
3. 用清理加召回释放空间。清理按简单、可预测的顺序进行，被清理的结果都可以召回；结果是否还有用，由模型在需要时通过召回判断（第 8 节）。
4. thinking 最后才压缩。客户端从不删除 thinking，`clear_thinking_20251015` 使用 `keep: "all"`；达到压缩阈值后，才由原生压缩处理被摘要范围内的推理。
5. 模型可见的内容尽量少，高效利用 token，遵循 SOTA 的 prompt engineering/context engineering 实践。模型只看到一个 `recall` 工具，插件不向系统提示添加内容；发给模型的文字固定，不含时间戳或计数器。状态和统计只在 `/context` 中给用户看。
6. 轻量，开箱即用。阈值由模型窗口和 Pi 的 `compaction` 设置得出，清理参数是内部常数；可选设置只有回退压缩的模型和 thinking 级别，而且可以在对话运行中进行热切换。
7. 回退压缩可以使用指定模型。原生压缩始终使用会话模型，使保留轮次的 thinking 继续有效。

保留 thinking 的依据来自模型厂商的测试。MiniMax 对 M2 的测试中，保留前几轮 thinking 后，
SWE-bench Verified 由 67.2 升到 69.4，τ²-Bench 由 64 升到 87，BrowseComp 由 31.4 升到 44.0。
Anthropic 在多轮编程测试中发现，max 强度下每个会话丢弃一次 thinking，输出 token 增加 20.1%；
第一轮之后每轮都丢弃，增加 67.1%。来源见[研究报告](references.md#研究报告)和
[Preserved thinking](references.md#服务商)。这些结果支持默认保留，不能证明每种任务下
保留全部历史都最优；实际任务通过率、费用和延迟仍需对照验证。

### 不变约束

1. 已保存的原始条目保持不变。客户端清理通过追加 `context_edit` 表达。
2. `tool_use` 与对应结果共同保留；一批工具结果未齐全时不压缩。
3. 压缩输出覆盖的范围和保留范围必须连续，不能漏掉或重复消息。
4. 只有完整、成功且仍适用于当前会话状态的压缩结果可以提交。
5. 使用模型的真实服务商、API、有效端点和模型标识判断能力。普通推理成功不代表压缩可用。
6. 未知能力、请求错误和统计缺失要明确表示。没有 thinking 的请求不能证明 thinking 保留成功。

以下是后续实现的文件划分，不是当前已有代码。

| ------------------------ | ------------------------------ | ----------------------- |
| `index.ts`               | 注册固定工具、命令和事件；装配模块              | 直接发送模型请求                |
| `session.ts`             | 读取当前分支；恢复插件条目；定位原文与压缩覆盖范围      | 选择清理策略                  |

| `edits.ts`               | 按第 8 节规则生成批量 `context_edit` 草案     | 修改 JSONL 或 thinking     |

| `compact.ts`             | 唯一压缩协调器；选择方法；检查取消、状态和覆盖范围      | 自己追加第二份压缩记录             |
| `providers/anthropic.ts` | 清理参数；原生摘要请求和完整响应；签名块检查         | 把 Pi 归一化错误当作成功          |
| `providers/openai.ts`    | 按 API 选择原生压缩协议；完整保留其状态         | 混用独立压缩与 Codex 流式压缩的窗口规则 |
| `fallback.ts`            | 用指定模型或会话模型生成 Pi 格式摘要           | 擅自切换到未配置的服务商            |
| `status.ts`              | `/context`、状态栏与有限诊断            | 添加模型提示或工具               |


使用普通函数和明确的数据类型连接这些模块，不引入新的插件框架、策略注册系统或数据库。
服务商模块只返回候选结果；提交由 Pi 的事件返回值完成。

## 4. 数据来源与持久化



### 4.1 召回的内容

召回恢复工具结果被清理前模型看到的内容。来源是当前分支的 Pi JSONL 中进入模型上下文的
顶层工具结果，召回内容与该结果的 `content` 逐字一致。`details` 不发送给模型，召回也不返回它。
Pi 已经截掉、且未保存的内容不能靠插件重建。

工具结果的长度在首次发送前由 Pi 和工具限制。Pi 的 `read` 和 `bash` 输出不超过 2,000 行或
50 KB；MCP 文本结果超过 20 KB 时去掉中间部分，完整内容写入临时文件。Pi 的扩展文档要求
其他工具自行截短，并告诉模型完整输出的位置。pi-pleat 不增加第二道截断：首次发送前的限制
已经存在，发送后又不能在客户端缩短（第 8 节）。不遵守该要求的工具会把完整结果送入模型，
这类结果由正常的清理和压缩处理。

工具给出的 `fullOutputPath` 或输出文件路径只是引用，可能指向临时文件。召回时检查文件是否
仍然存在并报告结果，不承诺它长期存在。不能把后来重跑工具或重新读取已变化文件的结果当作原文。

带 `parentToolCallId` 的嵌套调用服务于调用它的程序，例如 codemode。Pi 不为这些调用保存
独立的结果条目；召回只覆盖最终送入模型的父工具结果。

### 4.2 存储位置

Pi 会话条目保留原始消息和分支关系，原文只存在于 Pi JSONL。原生压缩块或窗口放在压缩条目的
`details`；插件的小型状态放在带 `pi-pleat.*` 类型的自定义条目中，不加入模型上下文。
超长召回结果使用的临时文件每次从 JSONL 重新生成，不属于会话存储。

### 4.3 压缩记录

每个原生压缩结果至少记录以下信息：


| 字段                                         | 含义                                                              |
| ------------------------------------------ | --------------------------------------------------------------- |
| `version`、`strategy`                       | 插件数据格式和 Anthropic、OpenAI 独立压缩、Codex Responses-trigger 或 Pi 摘要方式 |
| `provider`、`api`、`endpoint`、`model`        | 生成结果的真实通道；端点不含凭据或秘密查询参数                                         |
| `firstCoveredEntryId`、`lastCoveredEntryId` | 被替换的连续前缀范围                                                      |
| `firstKeptEntryId`                         | 紧随前缀的保留条目                                                       |
| `payload`                                  | 完整签名块或完整返回窗口；Pi 文本摘要使用标准 `summary` 字段                           |
| 请求状态说明                                     | 验证回放所需的提示、工具和边界信息；不保存认证头                                        |


这是一份数据约定，字段的最终 TypeScript 类型在实现时定义。重启仅从当前分支重建状态。
不选择其他分支的压缩块，也不在最新压缩失效后偷偷回放更旧的块。

## 5. 运行流程与提交

```text
顶层 tool_result
  → Pi 持久化结果
  → turn_end
      → 计算预算
      → 生成清理草案，或准备一次压缩
      → 请求完成并检查结果
      → 返回边界条目给 Pi 提交
  → 下一次正常请求
      → 校验并回放适用的原生前缀
      → Anthropic 加入已支持的服务端清理配置
      → 观察实际用量与转换报告
```

运行中的主动压缩使用 `turn_end` 返回 `compaction` 草案。不得在这里调用 `ctx.compact()`：
Pi 1.2.0 的该入口会先中止当前运行，且不会自动恢复它。

手动 `/compact` 和 Pi 自动阈值压缩通过 `session_before_compact` 调用同一个协调器，并返回
`compaction` 结果。协调器本身不写压缩条目；各入口各自返回一次结果，避免重复提交或递归。
处理 Pi 的手动压缩时遵守其停止当前任务的既有语义。

协调器状态为 `idle → preparing → requesting → validating → idle`。每个会话同时最多一个
压缩操作。开始时记录当前会话、分支叶节点、实际模型、压缩范围与请求状态；完成后重新检查。
取消、切换会话/分支/模型或相关历史变化使候选结果失效。丢弃该结果，保持原有有效状态。

首版采用同步边界压缩。新消息的排队和继续执行交给 Pi；不自行启动另一个 agent。
`continue` 仅在确有待继续工作时请求，避免压缩完成后无限空转。

## 6. 请求边界与回放

`requests.ts` 保存插件观察到的序列化请求及其来源边界，用已经发送过的完整请求边界选择切点。
Pi 的 `keepRecentTokens` 是保留目标；安全边界优先。不仅检查数组下标，还要检查来源条目、
角色、工具配对以及提示和工具状态。

实际请求可能含 Pi 插入的 `output_config.effort` system 消息。Pi 的压缩 checkpoint 也会合并
之前的 system 状态。不能假定“替换摘要消息”就一定恢复了原来的 provider 前缀。

原生保留仅对已验证的 Pi 版本和扩展组合承诺。必须验证快照与最终 HTTP body 一致，
以及压缩后的 checkpoint 能重建相同的保留消息。无法证明边界、状态或覆盖一致时，
该候选不进入原生回放路径，改用明确的文本摘要路径。

两个服务商都压缩选定的、工具配对完整的连续前缀。OpenAI 独立压缩返回的整个窗口是**该前缀**
的新表示；Codex 流式压缩则按下节的客户端规则构建该前缀的新表示。然后仅追加未覆盖的保留后缀。
不要发送整个当前窗口去压缩后，又追加一份已覆盖的近期历史。
这使 Pi 的 `firstKeptEntryId` 保持明确，也避免依赖手动压缩结果类型尚未表达的 retain-none 行为。

连续第二次压缩应包含当前有效的原生前缀及新覆盖的内容。回放规则与第一次相同。
按摘要文字查找替换位置、固定删 `messages[0]`、丢弃返回窗口中的项目，都不作为实现方法。

## 7. 服务商与传输



### Anthropic

普通请求在 `before_provider_request` 加入清理参数，通过 `provider_stream_event` 观察
`applied_edits` 和 `input_transformations`。`clear_thinking_20251015` 使用 `keep: "all"`。

独立的 `streamSimple()` 调用不会自动触发这些扩展事件，必须显式接入回调。
但 Pi 1.2.0 还会把有效的 `compaction` 结束原因归一化为错误。因此正式的原生压缩路径应使用
官方 Anthropic SDK 读取完整原始响应，复用经验证的 Pi 请求快照和运行时提供的认证、
headers、有效 base URL 与传输设置，不以 Pi 的普通 assistant 归一化结果作为原生压缩结果。

请求携带 `compact-2026-09-04` 和 `compaction: {type: "summarize"}`，去掉不能同时使用的
`context_management`、强制工具选择和结构化输出格式等字段。使用会话原模型、提示、工具和
thinking 设置。适配器必须读取到合法完成状态、完整签名块及全部用量后才能返回成功；
流中断、取消或服务端错误均不能提交。认证、代理和请求头的复用是单独的上线验证门槛。

清理和压缩是两个独立能力。服务端不支持清理时，应停止注入该功能，并通过经过验证的 Pi
恢复路径重试原始正常请求一次，避免持续生成相同错误。此恢复接入尚需验证。

### OpenAI

支持独立压缩的 Responses 通道使用官方 OpenAI SDK。保留返回 `output` 的所有项目，
包括 opaque compaction 和其他保留项目，作为被压缩前缀的完整替代。

Codex 使用其官方客户端的 Responses-trigger 协议：向普通 Responses 输入末尾追加
`{type: "compaction_trigger"}`，等待 `response.completed` 和恰好一个完整 compaction 项。
复用 Pi 现有的 Responses 传输，通过独立调用的显式原始流回调捕获压缩项。
控制项不进入持久历史。这个协议没有返回一个可直接替换全部输入的完整窗口；
客户端保留规定的用户/控制消息，再放入完整的原生 compaction 项。

两种协议的窗口处理分别定义。不能把独立 `/compact` 的“完整 output 原样回放”
套用到 Codex 的流式响应，也不能把 Codex 的客户端保留规则套用到独立 `/compact` 输出。
简单文本 fixture 只验证保留普通用户消息的情况；开发者消息、工具结果、图片和多代理项
仍需单独验证策略与预算。

能力缓存按 `(provider, api, endpoint, model, feature)` 区分，feature 还区分压缩协议。
已测 Codex 独立压缩路径返回 404，只证明该路径不可用。Codex 原生路径按官方客户端源码查证，
不继续反复尝试旧路径。当前 API 对应的原生方法不可用时使用文本压缩。

跨服务商切换时不发送其他服务商的原生块。Anthropic 可读摘要可以作为文本交接；
OpenAI 的 opaque 窗口需要从本地原文生成一次可读摘要。客户端不删除原始 thinking；
是否能再次原生回放取决于当前覆盖范围和通道状态，不能承诺切回模型后全部推理自动恢复。

## 8. 清理与召回

Anthropic 的 preserved thinking 规定，客户端清空或缩短已发送的 `tool_result`，会使之后的
全部 thinking 失效。官方建议在首次发送前缩短结果，以后的清理交给服务端。因此工具结果的
长度只在首次发送前限制（见 4.1），发送后的空间由清理和召回释放。

### 8.1 清理规则

所有服务商使用同一顺序：上下文超过清理触发点后，从最早的工具结果开始清理，保留最近 K 次
工具调用，保留全部调用参数；一批达不到释放下限时不清理。K、触发点、释放下限和最小清理大小
是内部常数，初值见第 9 节。

Anthropic 由服务端执行这个规则。`clear_tool_uses_20250919` 的 `trigger`、`keep` 和
`clear_at_least` 分别对应触发点、K 和释放下限，`clear_tool_inputs: false` 保留调用参数。
服务端只按时间顺序选择，小结果也会被清理。客户端不能改为按大小或用途选择，因为客户端修改
会使之后的 thinking 失效。

其他服务商由 pi-pleat 在 `turn_end` 追加一批 `context_edit`，只替换超过最小清理大小的结果。
替换小结果省不了多少空间，却让模型失去内容。占位文字只由结果大小和召回 ID 决定，例如
`[Output cleared to save context (48 KB). recall id="c3d4e5f6"]`。如果同一分支上目标之后
已有 Claude thinking，跳过该目标，因为修改它会在切回 Claude 时使这些 thinking 失效。

### 8.2 判断结果是否还有用

清理时不逐个判断结果的用途，这个判断在召回时由模型完成。模型调用 `recall` 时知道自己需要
什么；清理时判断则要预测以后的需要，容易出错。清错一个结果的代价只是一次召回。

让模型自己选择清理目标，需要在每次请求中加入工具说明和结果 ID，每次选择多一轮调用，
并在不确定的时间改变前缀、重写缓存。用 Jev 这类分类模型逐个判断（扩展通过
`ctx.modelRegistry.classify()` 调用），需要用户另外配置分类模型服务商的凭据，要把会话内容
发给另一家服务商，每次判断增加延迟，结果也难以复现。在 Anthropic 上，这两种方式都只能
通过客户端修改生效，会使之后的 thinking 失效。

简单规则有对照数据支持：在 SWE-agent 和 SWE-bench Verified 上，只屏蔽较早观察结果的方法
比原始代理费用减半，解决率与 LLM 摘要相当，有时略高（[The Complexity Trap](references.md#研究报告)）。
阶段 6 统计清理后不久又被召回的结果。比例高时先调整 K 和触发点；仍不够时，再为非 Anthropic
通道评估分类模型。

### 8.3 召回工具

模型只看到一个工具，插件不向系统提示添加内容：

```ts
recall({ id?: string, query?: string })
```

工具说明约 40 tokens：

```text
Get the full output of an earlier tool call that was cleared to save context.
Pass `id` from a cleared-output note, or `query` (command, path, tool name, or text) to get the newest match.
```

两个参数必须二选一。`id` 接受占位文字中的召回 ID（即 Pi 条目 ID）或工具调用 ID，返回一行
来源说明和原内容，例如 `[c3d4e5f6 · bash "npm test" · 48 KB]`。`query` 在当前分支的工具名、
调用参数和结果文本中做关键词匹配，直接返回最新一条匹配，格式与 `id` 相同，末尾用一行列出
其他匹配的 ID（最多 5 个）。模型需要更早的结果时，再用其中的 ID 取回。

在 Anthropic 上，占位文字由服务端在它收到的请求中生成，Pi 本地历史仍是完整结果，所以
pi-pleat 无法在占位文字中加入召回 ID；首次发送前加入的 ID 也会随结果一起被服务端替换。
服务端保留调用本身（`clear_tool_inputs: false`），模型用其中的命令或路径作为 `query`，
多数情况下调用一次即可取回。最新一条不是所需结果时，模型会多读一份无用结果（最多 50 KB）
并再调用一次。这份结果早于随后取回的结果，清理时会先被移除；在 Anthropic 上，它在压缩前
仍计入完整历史的大小。

召回内容超过 2,000 行或 50 KB 时，按 Pi 的惯例返回开头部分和临时文件路径，由模型用 `read`
分段读取；该文件每次从 JSONL 重新生成。图片结果按原块返回。召回范围是当前分支，包括已压缩
的原条目。

召回结果作为新的工具结果追加，以后也会像其他结果一样被清理。返回值说明来源，以及内容是否
只是 Pi 保存的片段。文件缺失、ID 不属于当前分支或内容不可用时，用一句话说明原因和下一步。
召回不重跑旧命令，也不把取回的文本当作新指令执行。

## 9. 预算、统计与失败

压缩阈值沿用 Pi 的 `C − reserveTokens` 和 `modelOverrides`。普通请求用量和新增消息估算
用于预测下一次请求；Anthropic 还记录清理前的估算值，以保证不带清理参数的原生压缩请求仍能装入窗口。
缺少服务端统计时标记“估算”，不能把缺失值当零。

清理触发点 0.5T、释放下限约 0.1T、保留最近 8 次工具调用（K）和最小清理大小 1 KB
都是内部常数的初值，不开放为设置，由阶段 6 的对照结果确定。小窗口和候选不足时要限制
释放下限，不能机械套用固定 token 数。清理减少输入内容，并不保证抵消缓存重写费用。

清理触发点不影响 thinking，对压缩时间的影响也很小。Anthropic 的压缩请求不能同时带
`context_management`，要发送未清理的历史并装入窗口，所以 Anthropic 上的压缩时间只由完整
历史的大小决定。其他服务商在上下文到达压缩阈值之前，都会清理所有符合规则的结果；触发点早晚
只改变清理发生的时间。触发点控制两件事：从什么时候开始减少每次请求的输入，以及旧结果在上下文
中保留多久。触发点早，请求更早变小；触发点晚，模型更少需要召回，清理和缓存重写的次数也可能
更少。服务端清理多久重写一次缓存尚未实测；阶段 3 测出后，与阶段 6 的结果一起确定触发点。

原生压缩请求要预留摘要输出和 thinking 空间；回退模型按自己的窗口重新计算预算。
缩小摘要范围时同步调整保留范围。不能通过静默删消息解决超限。
提交前还要检查“替代前缀 + 扩大的保留后缀 + 待发送新内容”构成的下一请求能否装入窗口。
压缩请求和下一正常请求必须分别满足预算；没有同时安全的切点时保留历史并报告限制。

Anthropic 压缩用量读取 `usage.iterations` 中的 compaction 项；普通请求和压缩用量分开记账，
避免只读顶层零值或重复计费。


| 结果                   | 处理                                 |
| -------------------- | ---------------------------------- |
| 明确不支持清理              | 禁用该清理功能，经验证的恢复路径重试正常请求一次；不因此立即压缩   |
| 明确不支持原生压缩            | 记住该能力结果，转文本压缩；其他功能保持各自状态           |
| 网络中断、限流、服务过载         | 遵守服务商退避，最多重试三次；未恢复则考虑文本压缩          |
| 取消或会话状态变化            | 丢弃候选；不重试、不进入回退                     |
| 认证/权限错误、无效请求、无法确认完整性 | 保留历史，明确报告；不归类成“模型不支持”              |
| 原生压缩可恢复失败            | 使用 `fallbackModel`；未设置时用会话模型       |
| 指定回退模型失败             | 只有换到 Pi 默认路径有实际意义时再尝试，避免同模型同请求重复失败 |


回退摘要沿用 Pi 格式和工具序列化。它可能使保留的 Claude thinking 失效，应记录原因并提示，
不声称推理原样保留。所有允许的方法均失败时保持原历史并报告错误。

首版可选设置只有 `fallbackModel` 和 `fallbackThinking`，配置归属 `pi-pleat`。
`/context` 展示有效/原始用量与估算标记、清理/压缩用量、原生能力状态、召回统计和
服务端报告的 thinking 丢弃。`prefix_binding_mismatch` 是现象，不能直接归因于某个插件。

## 10. 开发前必须补齐的证明

完整原生流处理、Pi checkpoint 后的请求重建、实际工具清理与召回、原生块重启恢复、
取消和状态变化，都仍是验证门槛。仅把原生块存在 JSONL 中不等于恢复已通过；
能从回放窗口读到标识也不等于摘要保留质量已通过。

先通过这些局部验证，再逐个实现上表模块。首版是否支持某个通道由通过的验证决定。
