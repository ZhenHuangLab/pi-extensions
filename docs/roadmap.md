# 验证与开发顺序

当前目标是确定框架并验证 Pi 和服务商契约。生产插件留待下一阶段。
结果中的“通过”只覆盖实际检查过的模型、通道、版本和行为。

| 阶段 | 要解决的问题 | 开始下一阶段的条件 |
| --- | --- | --- |
| 1. 宿主契约 | 自动压缩提交、独立回调、嵌套结果、分支投影和持久化 | 本地确定性检查通过，依赖版本固定 |
| 2. 原生响应与回放 | Anthropic 完整终止、iterations 用量、请求字段一致性、Pi checkpoint 与保留前缀 | 真实签名 thinking 存在；非空工具定义及配对结果通过；checkpoint 重建和落盘重启通过 |
| 3. 清理与原文 | 触发 applied_edits、顶层输出保存、查询后按 ID 取回、临时文件失效 | 原文逐字一致；嵌套程序值不变；分支不越界；存储失败可见 |
| 4. 失败与通道切换 | 不支持能力、取消、过载、认证失败、模型切换、回退模型预算 | 不重复提交、不丢消息；失败分类与费用统计正确 |
| 5. 插件实现 | 按 architecture.md 装配模块、命令和工具 | 各功能只声明已通过验证的范围 |
| 6. 效果评估 | 与 Pi 默认压缩、只清理对照 | 多次任务通过率、总费用及延迟支持默认参数 |

## 当前阻塞与待验证项

- **原生响应完整性：** Pi 1.2.0 报 `Unhandled stop reason: compaction`。已有实验只能证明
  捕获的签名块可回放；正式路径必须完整处理原生流、错误及取消。
- **请求重建：** 需要覆盖 Pi 压缩 checkpoint、会话内 system/effort 消息、工具变化、
  重启和分支选择。无法证明精确边界时使用文本摘要，不猜测替换位置。
- **Codex 独立压缩：** 已测试的订阅路径返回 404。保留失败记录；其他通道或原生方法另行验证，
  不将 404 改成测试通过。
- **实际服务端清理：** 小请求只证明配置被接受，还需要确认 `applied_edits`、缓存成本和召回。
- **附件：** 插件输出文件在 fork、目录迁移、缺失或写入失败时的行为需要单独验证。

## 验证纪律

连续压缩时，被替换的覆盖范围和保留后缀必须恰好包含每个来源条目一次。覆盖完整工具批次，
并验证自动/手动压缩同时触发，以及响应完成后、提交前发生取消或分支/模型切换的情况。
失效候选不得产生压缩条目，也不得发起回退请求。

直接拼接原生块的回放和 HTTP 字段断言不证明 Pi checkpoint 或重启恢复。阶段 2 必须通过
Pi 重建真实请求，并比较保留的序列化消息和覆盖范围，不能只检查回复中是否还有某个标识符。
现有 Anthropic 合成请求没有工具定义，其空值比较不能代替非空工具及工具结果的验证。

本地检查使用真实 Pi 会话机制和合成 provider。真实接口检查显式启用，并只发送合成内容。
不保存认证信息、签名、encrypted state 或 thinking 文本到公开日志。

每次记录命令、依赖版本、实际通道、通过范围和未通过项。新增断言之后，旧运行日志仍只证明旧断言。
只有新改动、失败或未解决的具体问题才触发重跑，不重复消耗真实模型请求来获取相同结论。
